## Резюме

**Ответ «что происходит с сообщением, если получатель офлайн 3 дня»:** ничего не происходит — и не только 3 дня, а никогда. `DaemonRequest::SendMessage` (handler.rs:61-76) создаёт `StoredMessage{sender_is_self:true, expires_at:None}` и пишет его в таблицу `messages` через `messages::store` (handler.rs:72); в `pending_messages` 1:1-текст НЕ кладётся, ratchet не применяется (в daemon нет ни одного вызова `sessions::save/load`, `RatchetSession`, `handshake::*` — единственные вызовы `sessions::save` — в backup.rs:182,205), `pending::dequeue/peek` в production не вызываются, `RelayClient` не создаётся, `dedup::is_duplicate` не вызывается нигде кроме своих тестов. Клиент получает `DaemonResponse::Ok` (= «отправлено»), сообщение остаётся в локальной истории навсегда (TTL-GC main.rs:167-177 удаляет только по `expires_at`, который для исходящих никогда не выставляется — он ставится лишь в `mark_read`, messages.rs:123). Через 3 дня, 3 месяца и после возврата получателя в сеть — у получателя ничего нет. Для групп/файлов чуть иначе: `SendGroupMessage`, `GroupControl` и `FileStart` кладутся в `pending_messages` (handler.rs:316, 470, 909) как **plaintext** `PlainPayload` postcard-байты, таблица PENDING не шифруется storage-ключом (lib.rs:123-124, pending.rs:3-4), лимитов/TTL у очереди нет, и её никто не читает.

**Что минимально нужно добавить в daemon для сетевой интеграции** (точки подключения):
1. `main.rs:100-160` — после `Storage::open` поднять `aira_net::endpoint::AiraEndpoint::bind(Some(secret_key))` (endpoint.rs:45), где `secret_key` детерминированно из seed (новый KDF-контекст, напр. `aira/iroh/identity/0` — в docs/KEY_CONTEXTS.md его нет: там только relay/mailbox/v1 и obfs/reality, строки 74-95), затем `protocol::build_router(&ep, ChatHandler::new(n), HandshakeHandler::new(n), Arc<RelayServer>, Some(&blob_store))` (protocol.rs:178-195) — получить `mpsc::Receiver<IncomingMessage>` (protocol.rs:26-31) и `Receiver<IncomingHandshake>` (protocol.rs:102-109).
2. Новый модуль `aira-daemon/src/net_task.rs` (или `session.rs`): `SessionManager {HashMap<pubkey, RatchetSession>}` — при старте `sessions::list_contacts` (sessions.rs:77) → `sessions::load` (sessions.rs:44) → `RatchetSession::from_snapshot` (ratchet.rs:484); после КАЖДОГО send/recv `to_snapshot` (ratchet.rs:440) → `sessions::save` (sessions.rs:20) **до** отправки в сеть (иначе crash между send и save = повтор counter/ключа цепочки).
3. `handler.rs:29-36` `handle_request` — синхронный `Fn(DaemonRequest)->DaemonResponse` (ipc.rs:62), вызывается прямо в tokio-таске (ipc.rs:144, 239). Нужно либо сделать async, либо добавить `net_tx: mpsc::Sender<NetCommand>` в аргументы: `SendMessage` → зашифровать ratchet'ом → `pending::enqueue(cid, postcard(EncryptedEnvelope))` → `net_tx.send(Deliver{cid})`; аналогично `enqueue_group_control` (handler.rs:300-320), `handle_send_group_message` (441-477), `handle_send_file` (863-949).
4. `pending_drain` таск: `pending::peek` (pending.rs:45) → `ep.connect(addr, alpn::CHAT)` (endpoint.rs:115) → `connection::write_framed` (connection.rs:27) → ack → `pending::dequeue` (pending.rs:67); триггеры: старт, входящее соединение, backoff-таймер; fallback — `RelayClient::new(ep, relay_addr).deposit(mailbox_id, envelope)` (relay.rs:353, 383) с `mailbox_id = derive_mailbox_id(shared_secret)` (relay.rs:85).
5. Входящий путь: `IncomingMessage{from, message}` → ratchet decrypt (ratchet.rs:323 проверяет MAX_ENVELOPE_SIZE) → `dedup::is_duplicate` (dedup.rs:18) → существующий `handle_incoming_payload(storage, seed, sender_pubkey, payload_bytes, &event_tx)` (handler.rs:621-674) — он уже рассылает `DaemonEvent::MessageReceived`; `ContactOnline/Offline` (types.rs:308-310) — по `ConnectionManager::set_connected/set_disconnected` (connection.rs:155-172).
6. Storage: `ContactInfo` (types.rs:13-24: pubkey, alias, added_at, verified, blocked) не содержит iroh `EndpointAddr` — демон не знает, куда звонить. `InvitationLink` (discovery.rs:20-30) несёт `endpoint_addr_bytes`, но `DaemonRequest::AddContact{pubkey, alias}` (types.rs:28-33) его отбрасывает. Нужны: поле `endpoint_addr: Vec<u8>` + `relays: Vec<..>` в ContactInfo (миграция схемы), ключи `settings` `relay/endpoints`, `net/...` (конвенция уже есть: `relay/url` в settings.rs:3, `transport/mode` handler.rs:19), env `AIRA_RELAY` для первого запуска, `DaemonRequest::{SetRelay, GetNetStatus}`, `DaemonEvent::DeliveryState{id, Sent|Queued|Relayed|Delivered}`.
7. Перед всем этим — миграция iroh 0.97→1.1 (по данности: публичные relay n0 отключаются 30.09.2026), `Endpoint::empty_builder` (endpoint.rs) уже ломается на 1.x.

Итог по крейтам: storage-слой (redb, ChaCha20-Poly1305 на значения, ключ `aira/storage/0` из seed — main.rs:101, KEY_CONTEXTS.md:15) и IPC (Unix socket / named pipe, 4-байтный LE length prefix, лимит 1 MB — ipc.rs:4, 15) работают и покрыты unit-тестами (storage 84, daemon 53), production-путях нет unwrap/expect/panic/unsafe (awk-скан всех src, `#![deny(unsafe_code)]` lib.rs:19). Но всё, что касается доставки — pending, dedup, sessions, relay, transfers, device sync — библиотечный код без потребителя.

## Находки

### [blocker] Сетевой путь в демоне отсутствует: сообщения никогда не покидают локальную БД

- **Evidence:** handler.rs:61-76 SendMessage → только messages::store, без pending::enqueue, без ratchet; main.rs:100-160 не создаёт AiraEndpoint/Router/RelayClient; grep по всем крейтам: sessions::save только backup.rs:182,205; pending::dequeue/peek только в тестах handler.rs:1076,1226,1467; dedup::is_duplicate только dedup.rs; handle_incoming_payload (handler.rs:621) только из теста :1322. Сетевые примитивы готовы, но без потребителя: AiraEndpoint::bind/connect/accept (endpoint.rs:45,115,129), build_router + ChatHandler/HandshakeHandler (protocol.rs:38-195), RelayClient::deposit/retrieve/ack (relay.rs:383,409,420), ConnectionManager (connection.rs:131-190).
- **Impact:** Клиент показывает «отправлено», получатель не получает ничего ни онлайн, ни через 3 дня. Релиз в таком виде невозможен. Все остальные offline-механизмы (pending, dedup, sessions, relay) — мёртвый код.
- **Recommendation:** См. summary, пункты 1-7: net_task в main.rs после Storage::open; SessionManager с load/save snapshot (sessions.rs:20,44; ratchet.rs:440,484) — save ДО отправки; handle_request получает mpsc::Sender<NetCommand> или становится async; SendMessage/группы/FileStart → ratchet-encrypt → pending::enqueue(EncryptedEnvelope) → прямая доставка → fallback deposit в relay; входящие IncomingMessage → decrypt → is_duplicate → handle_incoming_payload; ContactOnline/Offline из ConnectionManager. Сначала миграция iroh 0.97→1.1 (endpoint.rs).

### [high] pending_messages хранит plaintext (в т.ч. sender chain keys групп) в нешифруемой таблице

- **Evidence:** pending.rs:3-4 и lib.rs:123-124: таблица PENDING исключена из storage-шифрования «потому что там уже ratchet-encrypted envelope»; фактически enqueue_group_control кладёт postcard(PlainPayload::GroupControl) (handler.rs:305-316) с creator_sender_key (:430) и SenderKeyUpdate.new_key (:602-606), SendGroupMessage — PlainPayload::Text (:464-470), SendFile — FileStart с именем/хэшем файла (:901-909).
- **Impact:** Открытый текст групповых сообщений и групповые ключи лежат на диске в aira.redb без шифрования; при реализации сети формат очереди придётся менять (миграция).
- **Recommendation:** Зафиксировать инвариант: в PENDING только postcard(EncryptedEnvelope) после ratchet (как обещает pending.rs:3 и spec/04-protocol-wire.md:196-197); до этого — шифровать значения PENDING storage-ключом как остальные таблицы; добавить debug_assert/тип-обёртку PendingEnvelope вместо &[u8].

### [high] Очередь pending без лимитов, TTL и порядка по ratchet-counter

- **Evidence:** pending.rs:21-36 enqueue без проверки count/размера; нет поля timestamp/expiry; порядок — локальный seq через полный скан next_seq_for (pending.rs:157-173), count — O(n) итерация (pending.rs:104-117). Spec: 1000 сообщений / 100 MB на контакт, порядок по counter (spec/04-protocol-wire.md:199-203).
- **Impact:** Неограниченный рост БД при долгом офлайне контакта; O(n) на каждый enqueue; после реализации сети нельзя отличить «протухшее» сообщение от актуального.
- **Recommendation:** Добавить в значение заголовок {enqueued_at, size} или отдельную таблицу pending_meta; enforce 1000/100 MB с DaemonResponse::Error(QueueFull); хранить per-contact счётчик seq в settings/отдельной таблице вместо скана; GC по TTL (7 дней как у relay, relay.rs:112) в периодическом таске main.rs.

### [high] Dedup не подключаем к сети: у EncryptedEnvelope нет message_id

- **Evidence:** dedup.rs:18 ключ — [u8;16] message_id; proto.rs:23-30 EncryptedEnvelope{nonce, counter, ciphertext}; StoredMessage.id генерируется получателем rand_id (handler.rs:639, 658); is_duplicate нигде не вызывается.
- **Impact:** При relay-доставке + retry (spec/08-protocol-security.md:52) дубликаты не отфильтруются; ratchet при повторе того же counter выдаст ошибку, но для skipped-keys окна дубликат может пройти дважды в историю.
- **Recommendation:** Ключ дедупа = BLAKE3(sender_pubkey ‖ envelope.counter ‖ nonce)[..16] или (sender, counter) — вызывать is_duplicate до ratchet-decrypt в net_task; либо добавить message_id в PlainPayload (изменение wire-формата).

### [high] IPC без аутентификации и без ограничения прав на сокет/пайп

- **Evidence:** ipc.rs:66-114 UnixListener::bind без set_permissions (grep 0o600/set_permissions/peer_cred — 0); ipc.rs:164-209 Windows ServerOptions без security descriptor, first_pipe_instance(false) (:182), фиксированное имя \\.\pipe\aira-daemon (main.rs:68). Любой подключившийся может Shutdown (types.rs:81), ExportBackup{path} в произвольный путь (:51), ImportBackup, SendMessage.
- **Impact:** На Windows любой локальный процесс/пользователь может управлять демоном и выгрузить расшифрованный бэкап (backup.rs:66-76 кладёт расшифрованные ratchet snapshots); второй пользователь на той же машине не может запустить свой демон (коллизия имени), возможен pipe squatting.
- **Recommendation:** Unix: chmod 0700 на ~/.aira и 0600 на сокет сразу после bind, проверка SO_PEERCRED uid. Windows: имя пайпа с SID/именем пользователя, first_pipe_instance(true) для первого экземпляра, security descriptor «только текущий пользователь» (tokio ServerOptions::security_attributes или windows-sys), плюс простой auth-токен в файле <data_dir>/ipc.token (0600) в первом кадре.

### [medium] Синхронный handler блокирует tokio runtime; чтение файла до 4 GiB в память

- **Evidence:** ipc.rs:62 RequestHandler = Fn(DaemonRequest)->DaemonResponse, вызов в async-таске ipc.rs:144/239; handler.rs:895 std::fs::read(&path) для BLAKE3 при MAX_FILE_SIZE 4 GiB (blobs.rs:22); redb write-транзакции синхронные. Spec/10-daemon-ipc.md §8.1 требует spawn_blocking для тяжёлых операций.
- **Impact:** Один SendFile большого файла подвешивает все IPC-соединения и (после интеграции) сетевые таски; OOM при файлах в гигабайты.
- **Recommendation:** Сделать handle_request async (или обернуть вызов в spawn_blocking в ipc.rs), хэшировать файл потоково (blake3::Hasher + tokio::fs) внутри уже существующего tokio::spawn (handler.rs:914).

### [medium] Форвардер событий IPC умирает молча при отставании клиента

- **Evidence:** ipc.rs:129 и :224 `while let Ok(event) = event_rx.recv().await` — broadcast::RecvError::Lagged завершает цикл; ёмкость канала 256 (main.rs:120).
- **Impact:** После всплеска >256 событий (drain очереди при возврате контакта, FileProgress) GUI/CLI перестают получать события до переподключения, без ошибки.
- **Recommendation:** Обрабатывать Err(Lagged(n)) — логировать и продолжать (можно послать событие Resync), закрывать только на Closed; поднять ёмкость до 4096.

### [medium] Backup не покрывает группы, устройства, псевдонимы, counter и pending

- **Evidence:** backup.rs:27-36 BackupData = contacts, settings, ratchet_states, messages; restore backup.rs:160-191; pseudonyms::next_counter стартует с 0 при отсутствии записи (pseudonyms.rs:26).
- **Impact:** Восстановление на новом устройстве теряет группы (и sender keys), связанные устройства; повторная деривация псевдонимов с counter 0 нарушает unlinkability §12.6 и может выдать контакту уже использованный pubkey.
- **Recommendation:** VERSION=2 бэкапа (backup.rs:23 уже версионирован): добавить groups, group_messages, devices, pseudonyms + pseudonym_counter; pending не бэкапить, но при restore выставить counter ≥ max(pseudonyms)+1.

### [medium] Нет версии схемы БД — любое изменение postcard-структур ломает существующие базы

- **Evidence:** Storage::open lib.rs:139-161 только open_table; grep migrat/schema_version/SCHEMA_VERSION/RepairSession — 0 совпадений; значения — postcard без тегов полей (messages.rs:20, contacts, groups). Для сетевого milestone придётся менять ContactInfo (адрес), формат PENDING, StoredMessage (delivery state).
- **Impact:** После обновления релиза старые aira.redb дадут StorageError::Serialization на каждом чтении; пользователь потеряет историю.
- **Recommendation:** Таблица meta {schema_version:u32}; при open — цепочка миграций; для первого релиза зафиксировать v1 и написать миграцию v1→v2 вместе с изменением ContactInfo.

### [low] Storage-шифрование без AAD и без привязки к таблице/ключу строки

- **Evidence:** encrypted.rs:29-44 encrypt(nonce, plaintext) без associated data; один storage_key на все таблицы (lib.rs:125-128); nonce случайный 96-бит через rand::thread_rng (encrypted.rs:32-33).
- **Impact:** Злоумышленник с правом записи в aira.redb может переставить ciphertext между строками (например, подменить ratchet snapshot одного контакта другим) — не обнаружится. Коллизия nonce — ~n²/2^97, практически нерелевантна до ~2^32 записей, но save snapshot на каждое сообщение приближает к этому за годы.
- **Recommendation:** encrypt_with_aad(key, aad = table_name ‖ row_key, plaintext) через Payload{msg, aad}; опционально per-table subkeys (BLAKE3 derive_key от storage_key, задокументировать в KEY_CONTEXTS.md).

### [low] Ключ messages (contact_id, timestamp_micros) — коллизия в одну микросекунду затирает сообщение

- **Evidence:** messages.rs:3, 27 table.insert((contact_id, msg.timestamp_micros)) — insert заменяет; timestamp назначается получателем now_micros() (handler.rs:642, 661).
- **Impact:** При drain очереди/relay retrieve пачки сообщений в цикле возможны одинаковые микросекунды → потеря сообщений в истории.
- **Recommendation:** Ключ (contact_id, timestamp_micros, id[..8]) или монотонный счётчик; либо проверка занятости ключа с инкрементом.

### [low] TTL-GC делает полный decrypt всех сообщений каждые 30 секунд

- **Evidence:** messages.rs:146-169 delete_expired итерирует MESSAGES и decrypt_value каждую запись; main.rs:167-177 интервал 30 с; то же в runtime.rs:104-110 (Android).
- **Impact:** На истории в десятки тысяч сообщений — постоянная нагрузка CPU/батареи, особенно на Android.
- **Recommendation:** Вторичная таблица expiry (expires_at → key) или хранить expires_at в ключе/незашифрованном префиксе; интервал 5 мин.

### [low] Отправитель файла получает FileComplete без передачи

## Открытые вопросы

- Откуда демон возьмёт iroh EndpointAddr контакта: ContactInfo (types.rs:13-24) без адреса, AddContact{pubkey, alias} (types.rs:28-33) отбрасывает endpoint_addr_bytes из InvitationLink (discovery.rs:20-30). Решение — расширить ContactInfo + AddContact (миграция схемы) или полагаться на iroh discovery по EndpointId, выведенному из pubkey? (второе требует детерминированной связи identity→EndpointId).
- Должен ли iroh SecretKey демона выводиться из seed (стабильный EndpointId = линкуемость по сети) или генерироваться случайно на устройство и храниться в settings (лучше для §12.6, но нужна публикация адреса контактам)? Нужен новый KDF-контекст в docs/KEY_CONTEXTS.md.
- Ratchet-сессия хранится по contact pubkey (sessions.rs:4), а GetMyAddress выдаёт новый псевдоним на каждый вызов (handler.rs:77-95): по какому ключу контакт ищет сессию входящего сообщения — по псевдониму или по identity? Нужна таблица pseudonym→contact или включение pseudonym в IncomingMessage.
- SendGroupMessage fan-out (handler.rs:466-471) проходит по всем group.members — включает ли список собственную запись отправителя (лишний enqueue самому себе)? Не проверено.
- Стратегия persist ratchet snapshot: сохранять до отправки каждого сообщения (безопасно, +1 redb write-txn на сообщение) или батчить? При батчинге crash = повтор chain key.
- Android (FFI runtime.rs:95-125 без сети, dataSync FGS ≤ 6 ч/сутки по данности аудита §4.1): будет ли net_task общим кодом daemon (lib) для FFI, и как обрабатывать relay retrieve по push?
- Формат ключа дедупа для сети: (sender, counter) или хэш envelope; менять ли wire-формат PlainPayload ради message_id (совместимость с уже выпущенными v0.3.5 клиентами не критична, так как сети у них нет).
