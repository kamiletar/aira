# PoW при создании identity и anti-abuse — результат исследования (2026-09-07)

> Источник: raw `raw/a6a6c3c36573ff5a4.json`. Выжимка — в `../release-audit-2026-09.md` §5.

## Резюме

Идея «ресурсоёмкий PoW при создании первого ключа» в Aira почти ничего не даёт против двух заявленных целей. (1) Ботоводство: стоимость одноразовая и амортизируется — один «дорогой» identity даёт бесконечный спам, а спам-путь (ContactRequest) вообще подписывается pseudonym-ключом, не identity (crates/aira-core/src/spam.rs:32-35). (2) DDoS relay: депозиты на relay адресуются по mailbox_id = KDF(shared_secret) и никак не привязаны к identity (crates/aira-net/src/relay.rs:85, :231), а флуд QUIC-соединений бьёт по iroh-relay ещё до того, как Aira видит какой-либо ключ. Это подтверждает классический анализ Laurie/Clayton (PoW против спама не работает из-за ботнетов и медленных легитимных машин) и опыт Anubis (обход за «25 строк C», платят люди со слабыми устройствами). Кроме того, key-grinding ломает детерминизм seed→identity (identity.rs:32-33 → rustcrypto.rs:23-28): восстановление из фразы потребует повторного grinding'а (минуты на desktop, часы на телефоне/в браузере), а GPU (cuPQC: 6,5 млн ML-DSA-65 keygen/с на H100 против ~1e5/с на 8-ядерном desktop) даёт атакующему ~50× преимущество. Сейчас в коде PoW 20 бит BLAKE3 для ContactRequest существует, но не подключён ни в daemon, ни в handshake (нет вызовов solve_pow/verify_pow вне spam.rs); relay не имеет ни PoW, ни per-sender лимитов, ни глобального cap'а (RateLimited в relay.rs:75 никогда не возвращается). Рекомендация: НЕ добавлять PoW в onboarding; вместо этого (a) подключить per-action PoW (ContactRequest, регистрация/создание mailbox на relay, DHT publish) с адаптивной сложностью по образцу Tor (effort 0 по умолчанию, рост под нагрузкой, server nonce, TTL 30 с), (b) привязать relay-депозиты к аутентифицированному iroh EndpointId с GCRA per-NodeId + регистрацией mailbox получателем, (c) использовать встроенные лимиты iroh-relay (accept_conn_limit/burst, ClientRateLimit, AccessControl), (d) если владельцу всё же нужна «публично проверяемая цена identity» — сделать её Hashcash-штампом над детерминированным pubkey (nonce хранится/пересчитывается, ключ не меняется), а не grinding'ом ключа.

## Следствия для Aira

- PoW при создании identity не решает ни одну из заявленных задач: спам идёт через pseudonym-ключи (spam.rs:32-35), relay-депозиты не привязаны к identity (relay.rs:85,:231), QUIC-флуд бьёт по iroh-relay до Aira. Единственный реальный эффект — удорожание массового создания identity для Sybil в DHT (§11B.4) и обхода часового бана (spam.rs:23); на GPU это 41 с при 28 битах — не барьер.
- Key-grinding ломает детерминизм seed→identity (identity.rs:32-33, rustcrypto.rs:23-28): при восстановлении из фразы устройство обязано повторить grinding (минуты desktop, часы телефон/браузер) либо хранить счётчик вне фразы. Уже сейчас desktop/mobile соли Argon2 разные (seed.rs:33,:39) — вопрос портируемости identity между профилями надо закрыть до любых игр с деривацией.
- Argon2id m=256MB при создании seed — защита фразы от brute-force, а не анти-Sybil: она не публично проверяема и не должна использоваться как «PoW» (стоимость платит и пользователь при каждом восстановлении).
- Существующий PoW 20 бит для ContactRequest (spam.rs) не подключён нигде — первый шаг к релизу: подключить его в handshake/daemon, иначе «contact-first + PoW» из §13 существует только на бумаге.
- Relay сейчас без защиты: любой может создать неограниченное число mailbox'ов (relay.rs:231), нет per-sender лимита, RateLimited не используется (relay.rs:75), нет 1 GB cap из §11B.5. Это главный DoS-вектор на своём relay, и он закрывается лимитами/регистрацией mailbox, а не PoW на identity.
- Свой relay на mail-сервере: использовать штатные лимиты iroh-relay (accept_conn_limit/burst, ClientRateLimit, AccessControl по EndpointId — можно сделать relay «закрытым» для своих пользователей), версия ≥1.0.2 (crash-уязвимость). Per-IP лимиты вредят NAT-клиентам (issue #2967) — лимитировать по EndpointId.
- Adaptive puzzles §11B.2 — правильная модель (как Tor: effort 0 по умолчанию, рост под нагрузкой, server_nonce против precomputation, TTL 30 с), но таблица времён в спеке занижена ~5–10× для однопоточного BLAKE3; для браузера (WASM, один поток без SIMD) ещё ×3–5. Нужна калибровка «бит → секунды» на реальных профилях и Tor-подобный UX (оценка времени, рекомендация desktop).
- GPU/CPU: BLAKE3-PoW и ML-DSA key-grinding оба GPU-выгодны (≥50–1000×). Если нужна честность CPU/GPU — memory-hard puzzle (Argon2id с малой памятью ~2 MiB: GPU ~300%; Equi-X ≤10%), но у Argon2 верификация симметрична (столько же, сколько одна попытка) — годится только при малой сложности и обязательном rate limit до верификации («top half» атака по Tor).
- Браузер (M14): PoW/puzzle должен выполняться в Web Worker, ≤18–20 бит BLAKE3 или делегирование (NIP-13 «delegated PoW») с desktop-устройства того же аккаунта через multi-device sync; иначе Tier 3 в браузере под атакой просто отсекается (как в §11B.2 >95%).

## Рекомендуемый дизайн

ВЕРДИКТ. PoW в onboarding — НЕ делать. Причины: (1) амортизация — 1 identity = бесконечный спам, и спам-путь всё равно идёт через pseudonym-ключи (spam.rs:32-35); (2) DDoS relay не зависит от identity (relay.rs:85,:231; QUIC-флуд — уровень iroh-relay); (3) детерминизм seed→identity (identity.rs:32-33) ломается; (4) GPU-асимметрия 50–1000× (cuPQC 6,5M keygen/с vs ~1e5/с desktop); (5) платят легитимные пользователи со слабыми устройствами (Laurie/Clayton, Anubis, Tor UX). Argon2id 256MB на seed оставить как есть — это защита фразы, не анти-Sybil.

ЕСЛИ владелец всё же хочет «публично проверяемую цену identity» — вариант A «Hashcash-штамп над детерминированным pubkey», а не grinding ключа: IdentityStamp{nonce:u64, bits:u8, created_at} где verify = leading_zeros(BLAKE3(\"aira/identity-stamp/v1\" ‖ identity_pubkey ‖ bits ‖ nonce)) ≥ bits (переиспользовать spam.rs:71/96 с доменной константой). Ключ не меняется, восстановление из фразы работает; штамп пересчитывается в фоне после восстановления (или синхронизируется через multi-device sync). Штамп прикладывается к DHT-записи (§11B.4), invitation link, сертификату pseudonym-ключа (pseudonym подписан identity + штамп), регистрации mailbox на relay. Bits: 22 (desktop ≈ 0,5–1 с BLAKE3 многопоточно), одинаково для всех платформ, но mobile/browser считают в фоне/делегируют desktop-устройству. Честно: это лишь «мягкий» барьер Sybil для DHT (GPU 22 бита — миллисекунды), ценность низкая. Вариант B (grinding: seed_i = KDF(master, \"aira/identity/0/\"‖i) до выполнения условия, счётчик не хранится) — отклонить: повторный grinding при восстановлении, часы на телефоне/в браузере, усугубляет проблему разных Argon2-солей desktop/mobile (seed.rs:33,:39).

## Риски

- Ложное чувство защиты: PoW на identity создаст видимость анти-бот меры, не закрыв реальные векторы (mailbox-flood relay.rs:231, отсутствие подключённого PoW ContactRequest).
- Потеря аккаунтов: любой grinding в деривации без хранимого счётчика делает восстановление из seed-фразы долгим/невозможным на слабых устройствах; уже сейчас разные Argon2-соли desktop/mobile (seed.rs:33,:39) — риск, что фраза с desktop даёт другой identity на телефоне.
- GPU-асимметрия: атакующий с одним H100 (6,5M keygen/с) или GPU-BLAKE3 обгоняет desktop в 50–1000×; барьер для ботоводов — секунды, для честных мобильных/браузерных пользователей — минуты.
- «Top half» DoS верификатора: если ввести memory-hard puzzle (Argon2) с симметричной верификацией без rate-limit — проверка сама станет DoS-вектором (урок RandomX-Tor).
- Adaptive difficulty под атакой отсекает браузерных/мобильных пользователей (Tier 3) — нужен UX с оценкой времени и путь через контакт/приглашение (contact-first).
- Precomputation/replay puzzles: без server_nonce и replay-кэша (spec §11B.2) атакующий заранее считает решения; текущий PoW ContactRequest (spam.rs:49-55) не содержит ни nonce приёмника, ни timestamp — один решённый запрос можно переиспользовать бесконечно (нужно добавить recipient/timestamp в to_pow_bytes).
- Свой relay на mail-сервере: уязвимость crash-by-frame до iroh-relay 1.0.2; per-IP лимиты ломают NAT-клиентов; без AccessControl relay становится публичным ресурсом для чужого трафика.
- Расхождение спеки и кода: §11B.5 (PoW 16 бит, 30/min, 1 GB cap) и §13 (PoW 20 бит) не реализованы; при релизе документация обещает несуществующую защиту.
