## 0. Резюме

**Постановка владельца (23.09).** (1) Протокол нельзя превратить в паразитирующий прокси — во всех четырёх
смыслах: слив чужого трафика через relay сообщества, relay/хоп как выходной узел в интернет, mailbox как
бесплатное хранилище, чужой трафик с IP обычного пользователя. (2) IP пользователя скрывать от собеседника,
от оператора relay, от провайдера/DPI и от глобального наблюдателя. (3) Свой onion-слой поверх aira-relay.
(4) **Задействовать всех пиров как хопы** (как Tox/I2P), а не только opt-in серверы — «ты уж постарайся,
найди решение». (5) Тейк: «если список relay известен, РКН заблочит их влёт».

**Главный вывод: (1) и (4) не противоречат друг другу — при правильных инвариантах «все форвардят»
и есть основная защита от паразитов.** Паразитный прокси возникает не от того, *кто* форвардит, а от
четырёх свойств сети: есть выход в интернет; хоп соединяется с адресом, который ему прислали; кадры большие
и не тарифицируются; форвардеров мало относительно потребителей. Если каждое из этих свойств закрыто
протоколом (§4, инварианты AP-1…AP-7), то сеть умеет ровно одно — переносить маленькие тарифицированные
ячейки между нодами Aira до чужого mailbox, — и это уже не прокси, а мессенджер. А когда форвардит каждый
пользователь, ёмкость сети растёт вместе с нагрузкой (I2P живёт так с 2003 года), и «паразит» вынужден
привести свои ноды внутрь сети, где они тоже форвардят и тоже платят PoW. Ограничения на роль хопа нужны
только по **классу устройства** (мобильные, metered-сети, батарея) и по **юрисдикции** (hidden mode для
стран из strict-списка, как в I2P), а не из-за паразитов.

**Почему «все пиры» — единственный ответ на тейк про РКН.** Три сервера проекта блокируются за час; каталог
из 50 relay сообщества — за день (Tor: bridges из Moat и Snowflake блокировались в РФ в 2021, 11.2024 и
03.2026). Миллионы резидентных адресов с churn заблокировать без коллатерального ущерба нельзя. Но для этого
у сети **не должно быть глобального каталога**: точки входа распространяются через invitation link,
через уже установленный E2E-канал с контактом (friend-bridges, «darknet» Hyphanet) и через
rate-limited peer exchange по уже построенным маршрутам; ноды в strict-странах в hidden mode не публикуются
вовсе. Плюс транспорт первого хопа обязан не иметь DPI-сигнатуры: QUIC v1 iroh сегодня фингерпринтится
ТСПУ (байты версии `00 00 00 01`), а ALPN `aira/…` читается из QUIC Initial любым наблюдателем (RFC 9001:
ключи Initial выводятся из открытого DCID). Правильная точка встраивания обфускации — датаграммный
`CustomTransport` iroh 1.x (`socket/transports/custom.rs:24`), а не байтовые обёртки из удаляемого
`transport/*`.

**Что предлагается (§5, рабочее имя Aira Onion).** Каждая нода = клиент + хоп (+ опционально хост
mailbox, мост, iroh-relay — тема F). Хоп-идентичность отделена от чат-идентичности (иначе контакт найдёт
ваш IP в записях хопов). Ключи с каждым хопом устанавливаются один раз в сутки гибридным KEM
(X25519 + ML-KEM-768, уже есть `kem.rs::hybrid_encaps`) — постквантово, как в Outfox (Nym, WPES'25), но без
KEM на каждый пакет: ячейки идут под симметричными per-hop ключами по `key_id` (stateless для хопа, кроме
таблицы ключей и окна anti-replay). Допуск ключа = адаптивный PoW (`spam.rs::solve_pow`, как в Tor hspow) +
бюджет байт на ключ; у каждой ноды свой бюджет форвардинга (I2P share). Ячейки фиксированные (1 KB
полезных), маршрут фиксированной длины: отправитель выбирает 2 хопа (guard + middle), получатель — свои 2
для выгрузки, посередине — mailbox v2 (§4.3), которую никто не «выбирает по адресу из ячейки»: следующий
хоп задаётся только EndpointId из собственной таблицы ноды. Выхода в интернет нет по построению. Ответы и
push — через SURB (reply blocks). Профили: fast (1+M+1), standard (2+M+2), mix (2+M+2 + Loopix: Poisson-задержки
и cover-петли — против глобального наблюдателя, только desktop).

**Что это даёт по четырём наблюдателям (§1).** Собеседник — IP не видит уже в M19/M20 (relay-only endpoint
`clear_ip_transports()` + ссылка без прямых адресов), ещё до onion. Оператор relay/хопа — видит либо ваш IP,
либо адресата, никогда оба (2+M+2). Провайдер/DPI — видит зашифрованный UDP к резидентному адресу; это
устойчивость, а не невидимость (гонка вооружений, как у Tor). Глобальный наблюдатель — только в mix-профиле
ценой ~1,7 GB/мес cover-трафика и секунд задержки. Слово «невзламываемый» в документах не употреблять:
корректные обещания — в таблице §1.

**Находки по коду и планам (полный список §2):** HIGH — `AiraEndpoint::bind` всегда включает IP-транспорты
и hole punching (`endpoint.rs:56-95`), режима «только relay» нет, а iroh 1.2 его даёт одной строкой;
HIGH — план M19b/§3 net-audit кладёт в invitation link `postcard(ep.addr())`, а `Endpoint::addr()` содержит
LAN- и публичные IP — ссылка утечёт IP всем, через чей мессенджер её переслали; MEDIUM — `net_report`
шлёт пробы до 5 relay из RelayMap (`net_report.rs:497-505`) — каждый relay из списка узнаёт IP клиента, в
модели мостов RelayMap = только свои мосты; MEDIUM — mailbox v1/v2 видит IP и EndpointId депозитора
(`relay.rs:214-263`, §4.3); MEDIUM (план) — `accept_conn_limit/burst` в iroh-relay 1.2 «not currently
implemented» (`server.rs:486-500`), M20 п.4 на них рассчитывает; LOW — iroh-relay пишет IP клиента в
`info_span!` (`http_server.rs:499`); INFO — iroh 1.2.0 вышла 09.09.2026, M18 целить в `iroh = "1.2"`.

**Место в плане (§8):** предпосылки в M19/M20/M21 (relay-only по умолчанию, ссылка без IP, RelayMap = мосты,
mailbox принимает депозиты от форвардера с подписью sender внутри), затем **M24b Aira Onion v1 (4–6 недель)**,
**M24c мосты и обфускация (2–3 недели)**, **M24d mix-профиль (2 недели)**. До M24b честная формулировка в
THREAT_MODEL: «IP скрыт от собеседника; от оператора relay — нет».

**Решения владельца (§9):** дефолт hide-IP (relay-only) для беты; отдельная хоп-идентичность = второй
iroh-endpoint в демоне; strict-список стран и авто-hidden-mode; мобильные — только клиент; файлы в hidden
mode через «медленную полосу» или только direct с предупреждением; профиль по умолчанию standard или fast.

| Sybil-оператор многих хопов | н/п | н/п | guard-персистентность, разнообразие /16 и AS, вес по наблюдаемому uptime; всё же дешевле, чем в Tor (§6) | то же |

от любого одного оператора инфраструктуры; защита от провайдера — устойчивость к блокировкам, не

## 4. Принцип: почему «все форвардят» и «нет паразитов» — одно и то же требование

**Что делает сеть проксируемой.** Паразит хочет (а) дотянуться до произвольного адреса в интернете,
(б) прокачать много байт дёшево, (в) остаться незамеченным для тех, кто платит полосой. Tor-exit даёт (а),
Yggdrasil — (а)+(б), Snowflake — ничего из этого (доброволец доносит только до bridge). Мессенджер с
mailbox на конце маршрута может дать (б), если ячейки большие и бесплатные, и (в), если форвардеров мало и
они не видят нагрузки.

**Анти-паразитные инварианты (AP), обязательные для любого кода, который что-либо форвардит —
хоп, mailbox, клиент-relay, standalone aira-relay:**

- **AP-1 Нет выхода.** В протоколе хопа нет операции «соединись с host:port». Терминал любого маршрута —
  mailbox v2 (`Deposit`) на ноде Aira или SURB-ответ. Файлы, превью, всё внешнее — никогда через хоп.
- **AP-2 Следующий хоп — только из своей таблицы.** Ячейка несёт `next: EndpointId`; адрес хоп берёт из
  собственной таблицы нод/через свой relay, **не** из ячейки (`TransportAddr::Ip` в ячейке — невалидна).
  Иначе хоп превращается в распылитель QUIC Initial по чужим IP (reflection/сканирование). Реализуется
  `EndpointHooks::before_connect` (iroh 1.2 `hooks.rs:79-86`): отклонять `EndpointAddr` с IP не из таблицы.
- **AP-3 Ячейки маленькие и фиксированные.** 1 KB полезных, всё остальное — фрагментация. Ничего
  «потокового» через хоп не существует; 64-KB конверт = 64 ячейки, 1 GB = миллион ячеек с PoW-тарифом.
- **AP-4 Каждый байт тарифицирован.** Форвардинг только под `key_id`, выданным за PoW; у ключа бюджет байт
  и скорость; у ноды — общий бюджет форвардинга (`share`), fair queuing между ключами. Сложность PoW растёт
  с нагрузкой ноды (Tor hspow), поэтому под давлением платят те, кто давит.
- **AP-5 Хоп не отвечает за содержимое и не является источником.** Хоп общается только с нодами Aira,
  никогда с третьими сторонами; в логах mailbox депозитор — хоп, но авторизация депозита — подпись
  `sender_sk` внутри ячейки, поэтому наказывать хоп за чужой депозит нельзя и незачем (mailbox лимитирует по
  sender/owner, не по IP хопа).
- **AP-6 Хранилище — только зарегистрированные коробки.** Mailbox без `Register` владельца не создаётся
  (§4.3), регистраций ≤ N/сутки на ноду с PoW, квоты 10 MB/100 конвертов/7 дней, бюджет хранилища ноды.
  Паразиту достаётся «ненадёжный dead-drop на 10 MB за PoW» — хуже любого бесплатного файлохостинга.
- **AP-7 Ёмкость растёт с нагрузкой.** Форвардинг включён у всех, у кого он безопасен (desktop, unmetered);
  ноды паразита внутри сети тоже форвардят (иначе им не выдадут `key_id` дешевле базового PoW — см. §5.3
  про взаимность). Это I2P-модель: 20 лет без банка и без токена.

**Почему opt-in-only хуже.** (1) Мало форвардеров → каждый — ценная жертва для паразита и удобная цель для
блокировки; (2) публичный каталог opt-in relay = блок-лист РКН; (3) сеть не масштабируется с ростом
пользователей; (4) opt-in оператор с публичным доменом юридически заметнее, чем миллион одинаковых
резидентных нод, ни одна из которых не является источником чего-либо.

**Что остаётся честно нерешаемым.** Паразит может написать *своё* приложение поверх Aira-ячеек (C2
ботнета через mailbox, «файлообмен по 1 KB»). Это неотличимо от легитимного пользователя (E2E) и есть у
любого мессенджера (боты Telegram как C2). AP-3/AP-4/AP-6 держат это в классе «медленно и дорого», а
AP-1/AP-2/AP-5 гарантируют, что добровольцы при этом не становятся ни источником, ни выходом.

## 5. Дизайн «Aira Onion v1» (все пиры — хопы)

Рабочее имя; всё ниже — предложение для спеки (новый §5.5 в `spec/03-network.md`) и для M24b–M24d. Числа —
стартовые значения для обсуждения, не догма.

### 5.1 Роли, классы, две идентичности

**Роли в одной ноде** (флаги в `NodeRecord`, §5.2): `client` (всегда), `hop` (форвардер ячеек),
`mailbox` (хост коробок v2, §4.3), `bridge` (нелистингуемая точка входа для контактов), `relay`
(встроенный iroh-relay — только публичный IP + сертификат, тема F).

| Класс | Кто | hop | mailbox | bridge | листинг в peer exchange |
|---|---|---|---|---|---|
| `server` | standalone `aira-relay` (F) | да | да | да | да (если не hidden) |
| `desktop-public` | публичный IP или NAT с `mapping_varies_by_dest = false` (iroh `net_report`), сеть не metered, не на батарее | **да по умолчанию** | да (бюджет диска) | да | да, кроме strict-стран |
| `desktop-nat` | достижим только через свой relay (symmetric NAT) | да, вес ×0.3 (трафик идёт через его relay) | нет | да | да, кроме strict-стран |
| `laptop-battery` | на батарее / metered | да, share ×0.25 | нет | да | да |
| `mobile` | Android (iOS исключён) | **нет** (Doze, трафик, батарея) | нет | нет | нет |
| `hidden` (модификатор) | strict-страна (авто, см. §5.8) или выбор пользователя | только для контактов и их маршрутов | только для контактов | да | **нет** |

**Две идентичности.** У ноды две пары iroh-ключей и **два `Endpoint`** в одном демоне: чат-EndpointId
(из seed, M19 Phase A п.6 — его знают контакты) и **хоп-EndpointId** (случайный при установке, локальный
секрет, не из seed, ротируется по кнопке; в `docs/KEY_CONTEXTS.md` — как «не-KDF, локальный RNG»).
Причина: запись хопа содержит способ дойти до ноды (relay URL / IP); если она подписана чат-ключом,
любой контакт находит ваш IP в peer exchange — и «скрыть IP от собеседника» рушится. Цена — второе
relay-соединение (relay и так ваш guard, он видит оба ключа с одного IP — приемлемо). Хоп-ключи KEM
(`hop_x25519`, `hop_mlkem_ek`) — тоже локальные, ротация раз в неделю.

### 5.2 Запись ноды (`NodeRecord v1`) и её распространение

```rust
struct NodeRecord {
    version: u8,                 // 1
    hop_id: EndpointId,          // хоп-идентичность (Ed25519, iroh)
    hop_x25519: [u8; 32],        // KEM-ключи хопа для HopSetup (§5.3)
    hop_mlkem_ek: [u8; 1184],    // ML-KEM-768 encapsulation key
    class: NodeClass, caps: Caps { hop, mailbox, bridge, relay },
    relay_urls: Vec<RelayUrl>,   // как дойти до NAT-хопа (без IP!)
    share_hint_kbps: u16,        // объявленная полоса форвардинга
    obfs_psk_hint: Option<[u8; 8]>, // есть ли мост-обфускация (M24c); сам PSK — только контактам
    issued_at: u64, expires_at: u64, // 24 ч
    sig: [u8; 64],               // Ed25519 по hop_id над всем выше
}
```
≈ 1,4 KB (ML-KEM ek доминирует). Каналы распространения — **без глобального каталога**:

1. **Invitation link / QR**: не сама запись (QR не вместит), а `bridge_hint = hop_id ‖ relay_url` (≈ 80 B)
   одного–двух хопов приглашающего (его guard или он сам как bridge). Первое соединение — к этому хопу, и он
   отдаёт свою `NodeRecord` и до 8 соседних.
2. **E2E-канал с контактом**: `PlainPayload::BridgeOffer(NodeRecord + obfs_psk)` — контакт делится своим
   мостом/хопом (Hyphanet darknet, Tor «private bridge»). Единственный канал для `hidden`-нод.
3. **Peer exchange** по уже построенному маршруту: `GetPeers { n ≤ 8 }` под `key_id` (то есть за PoW,
   §5.3), не чаще 1/ч на ключ; отдаются только `listed`-ноды, которые отдающий **сам успешно использовал**
   за последние 24 ч (proof-by-use против Sybil-листинга).
4. **Якоря проекта**: подписанный список 3–5 нод в бинарнике — только если пусто; ожидаемо заблокирован в
   strict-странах, но нужен для первого запуска вне их.
5. pkarr (свой `iroh-dns-server`, M20) — опционально, только relay-URL хоп-ключа, никогда для `hidden`.

### 5.3 Установление ключа с хопом и допуск (`HopSetup`)

Клиент (любая роль) открывает iroh-соединение с хопом по ALPN `aira/2/hop` (напрямую или, для NAT-хопа,
через его `relay_urls`) и один раз в сутки на хоп делает:

```
HopSetup {
    key_id:   [u8; 8],          // случайный, выбирает клиент
    kem:      HybridCt,         // X25519 eph pk (32) ‖ ML-KEM-768 ct (1088) — kem.rs::hybrid_encaps
    pow:      { nonce: u64, bits: u8, slot: u32 },   // spam.rs::verify_pow над hop_id‖key_id‖BLAKE3(kem)‖slot
    want:     Budget { bytes: u32, rate_kbps: u16 },
    guard_proof: Option<NodeRecord + sig>,           // ТОЛЬКО для первого хопа (guard), см. «взаимность»
}
→ HopSetupOk { bytes, rate_kbps, expires_at, next_bits }  |  Busy { bits_required }
```

- `ss = hybrid_decaps(...)` (уже в `aira-core/src/kem.rs:85`); `k_hop = derive_key("aira/hop/key/v1", ss)`;
  подключи `aira/hop/fwd/v1`, `aira/hop/back/v1`, `aira/hop/surb/v1`. Постквантово (ML-KEM в
  HopSetup один раз в сутки, а не в каждой ячейке — это ровно упрощение Outfox: «KEM вместо DH, фиксированная
  длина маршрута», но с кэшированием ключа, чтобы ячейка не таскала 1088-байтный ct на каждый хоп).
- Состояние хопа на ключ ≈ 100 B: `{k_hop, bytes_left, token bucket, replay-окно 1024 бит по counter,
  expires}`; таблица ≤ 50 000 ключей (≈ 5 MB), LRU; вытесненный ключ → ячейка молча дропается → клиент
  делает `HopSetup` заново (дёшево, без потери сообщений: доставка подтверждается ответом H).
- `slot` = 10-минутное окно; PoW из другого окна невалиден → precomputation/replay невозможны (та же
  правка, что аудит §5.3 требует для `ContactRequest`).
- **Адаптивная сложность** (Tor hspow): `bits = base 16 + f(заполнение таблицы, утилизация share)`, до 24;
  при > 95 % — `Busy`. Легитимному чату нужно ~4 ключа в сутки (2 хопа × 2 направления); под атакой
  платит тот, кто создаёт ключи пачками.
- **Бюджеты (AP-4).** На ключ: 8 MB / 24 ч, 16 KB/s, одна очередь. На ноду: `share` (desktop-public
  по умолчанию 32 KB/s исходящих на форвардинг — I2P отдаёт 48 KB/s из 40 KB/s аплинка; месячный cap 3 GB;
  настраивается; `laptop-battery` ×0.25); fair queuing между ключами (DRR), при перегрузке — `Busy` новым
  и пропорциональное урезание существующим.
- **Взаимность без банка (AP-7).** Все схемы с «зачётом за форвардинг» (BRAIDS/TEARS/Nym) требуют банка или
  блокчейна и/или ломают анонимность (GoldStar). Вместо них — *мягкая взаимность на guard'е*: клиент,
  предъявивший guard'у свою свежую `NodeRecord` с `caps.hop = 1` и подписью, получает базовую сложность;
  без неё — `+4 бита` (×16 работы: 20 бит ≈ 0,2 с desktop, ~1 с телефон — терпимо для мобильных, которые
  хопами не бывают). Guard и так видит IP клиента, поэтому предъявление записи ничего нового не раскрывает;
  **на middle-хопах `guard_proof` запрещён** — иначе middle узнаёт, чей это маршрут. Guard может позже
  проверить запись «по факту» (использовать этот хоп сам — proof-by-use, §5.2 п.3); ноды, объявившие
  себя хопом и не форвардящие, выпадают из peer exchange и теряют скидку. Паразиту, чтобы платить меньше,
  придётся реально форвардить — то есть стать частью ёмкости сети.

### 5.4 Ячейка (`Cell v1`)

Фиксированный размер на проводе **1 280 B**: 3 слоя заголовка по 80 B + полезная нагрузка 1 024 B + 16 B тег.

```
Cell {
    layers: [Layer; 3],    // guard, middle, terminal — всегда три (фиксированная длина, как Outfox/Loopix; в fast-профиле middle-слой фиктивный)
    payload: [u8; 1040],   // 1024 данных + 16 AEAD-тег терминала
}
Layer (80 B) = key_id 8 ‖ counter 8 ‖ cmd 1 ‖ next_hop 32 (EndpointId или нули для терминала) ‖ pad 15 ‖ tag 16
```

- Хоп: находит `key_id`, проверяет `counter` по окну anti-replay, AEAD-расшифровывает **свой** слой
  (nonce = counter, AAD = позиция слоя), сдвигает слои (на место третьего кладёт псевдослучайный блок из
  `k_hop`, чтобы длина не выдавала позицию — приём Sphinx), снимает свой keystream с payload, списывает
  1 280 B с бюджета ключа, отправляет `next_hop` по своей таблице (AP-2). Никакого разбора payload на
  middle-хопах нет вообще.
- Терминал (H или адресат SURB): проверяет тег payload, читает `cmd` и тело: `Deposit{mailbox_id, frag,
  envelope_part}`, `Register`, `Retrieve`, `Ack`, `GetPeers`, `Wake`, `Drop` (cover).
- Фрагментация: конверт ≤ 64 KB → ≤ 64 ячеек `{frag_id 8, idx u8, total u8}` в payload; H собирает,
  неполный фрагмент через 60 с дропается. Текст с паддингом 256–512 B (`padding.rs:12`) = 1 ячейка,
  4 KB = 4 ячейки, накладные ≈ 25 %.
- Ответы: **обратное состояние на 30 с** — хоп помнит `(key_id → входящее соединение)` и гонит ответные
  ячейки назад по тем же ключам (`aira/hop/back/v1`) — дешевле, чем пачки SURB на каждый retrieve. SURB
  (Loopix-style, однократные, 1 ячейка) — только для асинхронного `Wake`: получатель оставляет у H
  запас из 16 SURB при `Register`/`Retrieve`, H тратит один на каждое «пришло письмо».
- Известное ограничение: tagging-атака (guard портит payload, сговорившийся H видит битый тег в тот же
  момент) требует сговора guard + H; смягчается персистентностью guard и cover-петлями mix-профиля
  (Loopix детектирует активные атаки петлями). В спеке — честно.

### 5.5 Маршрут: отправитель выбирает свои хопы, получатель — свои, посередине mailbox

```
S ── G_s ── M_s ──▶ H ◀── M_r ── G_r ── R
      ↑ выбирает S             ↑ выбирает R          H = хост mailbox v2, выбран R (2–3 реплики, N-of-M — тема F)
```

- **Deposit**: S → G_s → M_s → H; терминальный слой = `Deposit` с подписью `sender_sk` (уже в §4.3), H
  проверяет по зарегистрированному `sender_pk`. H видит только M_s. Никто не видит и S, и адресата.
- **Register / Retrieve / Ack**: R → G_r → M_r → H, ответ назад по обратному состоянию. H видит только M_r.
- **Push**: H → `Wake` по SURB → R делает `Retrieve`. Задержка доставки «оба онлайн» ≈ 1–3 с.
- Это композиция SimpleX (первый хоп — отправителя, второй — получателя) и Veilid (safety route +
  private route) с mailbox в точке склейки; rendezvous-схема Tor (RP) не нужна: mailbox уже есть в M21.
- **Профили**: `fast` — S→G_s→H, R→G_r→H (guard видит H; H видит guards; 1 хоп в каждую сторону,
  задержка минимальна); `standard` — как на схеме; `mix` — standard + §5.9. Профиль — на аккаунт, с
  переопределением на контакт.
- Контакт-запись (`ContactInfo`, M19 Phase A п.1): вместо `relays: Vec<RelayRef>` — `mailboxes:
  Vec<(hop_id: EndpointId, relay_urls, mailbox_id)>` (2–3), никогда IP. Смена H — подписанный
  `MailboxMigration` (§11B.5.1).

### 5.6 Guard'ы, разнообразие, Sybil, churn

- **Guard'ы**: 2 активных + 1 запасной из нод с uptime-оценкой ≥ 0,9 за 7 дней (клиент ведёт локальную
  историю успехов), держатся 30 дней (Tor держит месяцы; резидентный churn выше). Guard узнаёт IP клиента —
  один и тот же долго, а не 100 случайных нод в неделю.
- **Разнообразие**: G, M, H — разные /16 и (если есть данные) разные AS; для `hidden`-клиента — не из
  своей страны (правило I2P hidden mode).
- **Sybil дешевле, чем в Tor** (нет измерения полосы авторитетами): (а) листинг только proof-by-use (§5.2
  п.3), (б) вес по uptime, (в) guard-персистентность ограничивает окно наблюдения, (г) mailbox-хосты
  выбирает получатель из *своего* опыта, а не из чужого списка. Сговор G_s + H остаётся угрозой
  корреляции по времени (как в Tor) — это границы standard-профиля, mix закрывает.
- **Churn**: ячейки stateless, обратное состояние живёт 30 с; нет ответа от H за 5 с → повтор другим
  маршрутом (новый M, тот же G); H недоступен → следующая реплика. Хопы `desktop-nat` — вес ×0.3.

### 5.7 Файлы

Хоп переносит только ячейки; «потока» нет по построению (AP-3). Варианты по профилю:

| Профиль | ≤ 64 KB (inline в конверте) | ≤ 10 MB | > 10 MB |
|---|---|---|---|
| direct (per-contact opt-in, IP раскрыт этому контакту) | ячейки | iroh-blobs напрямую | iroh-blobs напрямую |
| hide-IP (relay-only, M19/M20) | ячейки | iroh-blobs через relay (relay видит обе стороны) | то же |
| standard / mix (M24b) | ячейки | «медленная полоса»: ячейки в mailbox H (квота 10 MB), марка PoW 20 бит на MB, 16 KB/s → 10 MB ≈ 11 мин | **недоступно**; UI предлагает direct с предупреждением |

Медленная полоса нарочно непривлекательна для массового трафика (AP-4) и при этом закрывает главный
бытовой случай — фото/голосовые ≤ 10 MB.

### 5.8 Против перечисления и блокировок (ответ на тейк про РКН)

1. **Нет глобального каталога.** Четыре канала §5.2; ни один не отдаёт «всех». Peer exchange отдаёт
   ≤ 8 нод за ключ в час → перечисление opennet стоит ~1 ключ (PoW) на 8 нод и часы времени; при
   1 млн нод ≈ 125 000 ключей ≈ 7 CPU-часов при 20 битах. Это **дёшево для государства** — как и
   краулинг Tox/Tor-консенсуса. Поэтому:
2. **Opennet и darknet одновременно** (Hyphanet). Листингуются только `desktop-public`/`server` вне
   strict-стран — их и так можно найти. Пользователи strict-стран автоматически `hidden`: не в листинге,
   форвардят только для контактов, входят в сеть через **мосты, полученные от контактов** (`BridgeOffer`)
   или из invitation link. Перечислить darknet можно только инфильтрацией социального графа. Строго:
   «все пиры форвардят, но не все пиры перечислимы».
3. **Определение strict-страны** — не GeoIP-база в бинарнике (нечего обновлять и тащить), а: локаль и
   часовой пояс ОС + страна публичного IP, которую сообщает *свой* relay (`net_report` даёт публичный
   адрес, relay проекта/сообщества может отдавать `country` в ответе) + явный выбор в онбординге с
   объяснением. Список — как у I2P (RU, CN, IR, … по Freedom House), решение владельца.
4. **Транспорт первого хопа (M24c).** Сегодня прямой QUIC iroh фингерпринтится ТСПУ (версия `00 00 00 01`;
   правило описано для UDP/443, но iroh слушает случайный порт — это отсрочка, не защита), а ALPN и
   TLS-параметры читаются из Initial (RFC 9001). Datagram-обфускация в `CustomTransport` (iroh 1.2
   `socket/transports/custom.rs:24-70`: `bind → CustomEndpoint { watch_local_addrs, create_sender,
   poll_recv }`): каждая датаграмма QUIC → `AEAD(k_obfs, nonce ‖ padding_len ‖ datagram)` без
   открытых полей, случайная длина, опционально «junk»-пакеты в начале (AmneziaWG). Ключ `k_obfs =
   derive_key("aira/bridge/obfs/v1", psk_моста)`; PSK — в `BridgeOffer`/ссылке, для листингуемых хопов —
   публичный из записи (тогда это защита от сигнатур, но не от активного зондирования — честно
   как «режим 2» §11A). Это **единственная** корректная точка встраивания обфускации в iroh; байтовые
   обёртки `transport/*` удаляются (net-audit §8), а идея сохраняется здесь.
5. **Relay-путь (WSS:443)**: SNI = домен relay и JA4 rustls — блокируются по домену/фингерпринту. Для
   relay сообщества — фронтирование через настоящий веб-сервер (WebTunnel-подход), тема F. Клиент в
   strict-стране должен предпочитать мосты-хопы по UDP, а relay — только через мосты.
6. **Snowflake-урок**: транспорт мостов должен быть заменяемым (DTLS-фингерпринт Snowflake прожил до
   03.2026); `CustomTransport` даёт это без изменения onion-слоя.

### 5.9 Mix-профиль (Loopix) — против глобального наблюдателя

- Каждый хоп задерживает ячейку на `Exp(λ)` (среднее 0,5 с; конфиг), клиент шлёт cover-петли (ячейка
  через 3 хопа и назад по SURB, `cmd = Drop`) с частотой 1 ячейка / 2 с, H тоже гоняет петли; реальный
  трафик неотличим от cover.
- Цена: ≈ 0,65 KB/s ≈ **1,7 GB/мес** на клиента и 2–4 с задержки; только desktop; анонимность
  против глобального наблюдателя ограничена числом одновременно активных mix-клиентов (Loopix: гарантии
  зависят от λ и размера множества). Включается на аккаунт; контакты в `fast`-профиле от этого не
  выигрывают.

## 6. Ответ на вопрос владельца: «а вдруг можно задействовать все клиенты?»

**Да — и нужно, но «все форвардят» ≠ «все одинаковы».** Ограничения приходят не от паразитов (их
закрывают инварианты §4 независимо от того, кто форвардит), а от трёх других вещей:

| Ограничение | Почему | Что делаем |
|---|---|---|
| Класс устройства | мобильный хоп = батарея, трафик, Doze; ноутбук на батарее/metered — то же в меньшей степени | `mobile` — только клиент; `laptop-battery` — share ×0.25; desktop unmetered — **хоп по умолчанию** (opt-out, не opt-in) |
| Юрисдикция | листинг хопа = «этот IP запускает Aira» (урок Tox), а форвардинг для незнакомцев в RU/CN/IR — риск для человека | `hidden` авто по strict-списку: форвардит только для контактов и их маршрутов, не листингуется, входит через мосты |
| Достижимость | symmetric NAT → хоп достижим только через свой relay: медленно и грузит relay | класс `desktop-nat`, вес ×0.3; всё равно хоп |

Что даёт «все пиры» помимо ёмкости: (1) точки входа не блокируемы списком (§5.8); (2) у каждой
резидентной ноды появляется правдоподобное отрицание — трафик с её IP может быть чужим (аргумент
I2P/Tor-relay); (3) чем больше активных нод в mix-профиле, тем сильнее гарантии Loopix. Чего «все пиры»
**не** дают: анонимности от сговора guard + mailbox без mix, и защиты от активного зондирования моста без
PSK.

**Чем это отличается от рекомендации «серверы + opt-in клиенты с публичным IP» (мой первый вариант).**
Opt-in остаётся только для роли `relay` (встроенный iroh-relay нужен NAT-нодам, требует сертификата и
стабильного адреса — тема F) и для роли `mailbox` (чужие данные на диске — осознанное согласие). Роль
`hop` — по умолчанию у всех, кому безопасно. Тема F в части «клиент как relay» не противоречит, а
дополняет: её резервирование N-of-M — это реплики H в §5.5.

**Остаточные риски, которые надо записать в THREAT_MODEL:** корреляция по времени при сговоре G и H
(standard-профиль); tagging-атака при том же сговоре; перечислимость opennet-хопов государством
(darknet-мосты — нет); Sybil дешевле, чем в Tor; хоп-идентичность связывает *все* ваши маршруты через один
guard с одним IP (это и есть смысл guard'а — меньше наблюдателей, но дольше); паразит-«в сети» (своё
приложение поверх ячеек) неотличим и ограничен только квотами.

## 10. Не проверено

- Ничего не компилировалось и не запускалось; все ссылки на iroh — по исходникам `iroh-1.2.0`,
  `iroh-relay-1.2.0`, `iroh-0.97.0` в `~/.cargo/registry` (скачаны `cargo fetch` в этой сессии).
- Поведение `clear_ip_transports()` — по doc-комментарию `socket.rs:13-14`; код обмена адресами при hole
  punching в 1.2 по имени `CallMeMaybe` не найден (переименован) — что без IP-транспортов пиру нечего
  сообщать, следует из отсутствия локальных адресов (`socket.rs:417-425`), не из прочтения самого обмена.
- `net_report`: `MAX_RELAYS = 5` относится к QAD-пробам (`net_report.rs:497-505`); HTTPS-пробы идут по
  всем relay из карты (`probes.rs:98-106`) — вывод «до 5 relay узнают IP» консервативен, может быть «все».
- `EndpointHooks::before_connect` получает `&EndpointAddr` (`hooks.rs:79-86`) — достаточно ли этого, чтобы
  отфильтровать адреса, которые iroh *сам* подставит из address lookup после хука, — не проверено;
  для AP-2 может понадобиться ещё и `addr_filter`/отключение lookup у хоп-endpoint'а.
- Страницы arxiv.org (Outfox) и blog.torproject.org недоступны из этого окружения (egress-блок): размеры
  Outfox и детали WebTunnel — по поисковым выдержкам; правило ТСПУ по QUIC — по статье IMC'22 (2022) и
  может быть шире сегодня.
